# SS-033 — Wildcard import from the Soroban SDK

- **Severity:** low
- **Confidence:** high
- **Category:** dependencies

## Problem

A contract imports everything from `soroban_sdk` with a glob:

```rust
use soroban_sdk::*;
```

Wildcard imports obscure which SDK items the contract actually uses. They also
make review harder: a deprecated, unsafe, or renamed API can enter scope without
an explicit diff, and future analysis cannot tell which symbols came from the
SDK. Nested globs such as `use soroban_sdk::token::*;` have the same problem.

This is a source-hygiene signal, not evidence of an exploitable vulnerability.

## How it is detected

For every parsed source file, the detector walks `syn::ItemUse` trees (including
`use` statements inside inline modules) and records every glob terminal whose
path is `soroban_sdk` or starts with `soroban_sdk::`. Projects must be classified
as Soroban or likely-Soroban before the rule runs.

The finding points at the `use` item and reports the offending path as
evidence, for example ``wildcard import `use soroban_sdk::*` hides which Soroban
SDK items are used``.

## Limitations

- Only source-level `use` trees are inspected. Re-exports generated by macros,
  `include!`, or build scripts are not expanded or resolved.
- A glob from a crate that re-exports SDK items is not detected.
- The rule does not judge whether a specific imported item is deprecated or
  unsafe; it only flags the wildcard itself.

## False positives

- Deliberate prelude-style modules that intentionally re-export a curated set;
  the finding is still accurate for reviewability but may be accepted.
- Test-only modules that never compile into the deployed contract.

## Remediation

Name the items the contract uses:

```rust
use soroban_sdk::{contract, contractimpl, symbol_short, Env, Symbol};
```

The same applies to nested paths: replace `use soroban_sdk::token::*;` with the
specific client or type required by the contract.

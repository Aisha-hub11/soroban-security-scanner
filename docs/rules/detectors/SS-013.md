# SS-013 — Cross-contract call before state update

- **Severity:** high
- **Confidence:** low
- **Category:** cross-contract

## Problem

A public contract entry point makes a cross-contract call before its first
storage write. Soroban permits reentrancy, so a malicious callee can be invoked
while the caller's state still reflects the pre-call values. The callee may
re-enter the caller or observe intermediate state that the author did not expect
to expose.

## How it is detected

For every public function inside a `#[contractimpl]` block, the detector orders
cross-contract call sites and storage-mutation calls by their byte span in the
source. A call is reported when it appears before the first storage mutation in
the same function. Calls through a local variable assigned from a
`SomeClient::new(...)` constructor are resolved directly; if no such call can be
resolved, the constructor itself is used as a conservative fallback.

The evidence records the call and mutation line numbers and byte offsets, which
is the ordering proof for the finding.

## Limitations

- The check is intraprocedural: cross-contract calls or state writes performed in
  helpers are not ordered against each other.
- A storage write is treated as any recognized mutator (`set`, `remove`,
  `update`, and TTL methods) on a receiver whose rendered text contains
  `storage`.
- Only client variables initialized from a `...Client::new(...)` call are
  resolved. Manually written interfaces or clients passed in as parameters are
  not tracked.
- The rule cannot prove that reentrancy is reachable or exploitable. It reports
  **low confidence** for that reason.

## False positives

- External calls that are intentionally made before any state change, where the
  contract holds no state that the callee can observe or exploit.
- Read-only entry points that delegate to another contract and never mutate local
  storage.
- Designs with an explicit reentrancy guard that makes the ordering safe.

## Remediation

Follow checks-effects-interactions: validate inputs, update all relevant contract
state, and only then invoke another contract. If an external call must happen
first, add an explicit reentrancy guard and document why the intermediate state
is safe to observe.

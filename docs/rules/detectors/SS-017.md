# SS-017 — Authorization after state mutation

- **Severity:** medium
- **Confidence:** medium
- **Category:** authorization

## Problem

A contract entry point mutates storage before calling `require_auth`. The
authorization check should run before the effect. A mutation that happens first
indicates a logic-ordering bug and can leave state changed on a path that should
have been rejected.

## How it is detected

Within a public `#[contractimpl]` entry point, the detector compares source byte
positions. It reports each storage mutation that occurs strictly before the
earliest `require_auth` / `require_auth_for_args` call. If the function has no
authorization call, SS-001 covers it instead and SS-017 stays quiet.

## Limitations

- Intra-function only; authorization or mutation inside a helper is not ordered
  relative to the caller.
- Reports the mutation, not the missing authorization semantics.
- A deliberate mutation before an authorization check may be a false positive.

## False positives

- Mutations that do not depend on the caller identity.
- Contracts that intentionally write audit state before rejecting a call.

## Remediation

Authorize the caller at the start of the entry point, before any storage change
that depends on the caller. Then perform the mutation.

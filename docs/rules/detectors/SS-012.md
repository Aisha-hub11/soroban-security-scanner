# SS-012 — Unbounded collection growth in an entry point

- **Severity:** medium
- **Confidence:** low
- **Category:** resource-usage

## Problem

An entry point reads a collection from storage, pushes a new item, and writes it
back without checking a size limit. Repeated calls can grow the ledger entry
without bound. Rent and read costs grow with the collection, and iteration or
serialization can eventually exceed Soroban resource limits, causing a denial of
service.

## How it is detected

For every public `#[contractimpl]` entry point, the detector requires:

1. a storage read (`get` on a `storage` receiver),
2. at least one storage mutation, and
3. a `push`, `push_back`, or `push_front` call,

and reports each growth call when the function does not contain a `len()` call
or a comparison mentioning `len()`.

## Limitations

- Heuristic; it cannot prove the collection is unbounded or attacker-controlled.
- Only `push`/`push_back`/`push_front` growth is reported. Growth through
  `Map::set` or custom collection helpers is not covered.
- A `len()` check anywhere in the function suppresses the rule, even if the
  check does not guard the mutation.
- Helpers called by the entry point are not traced.

## False positives

- Collections capped by a check performed in a helper.
- Collections whose growth is bounded by contract-controlled configuration and
  checked outside the analyzed function.
- Local collections that are never written back to storage (not reported).

## Remediation

Read the current length and reject the operation at a documented maximum before
growing the collection. Prefer bounded aggregates when possible, and return a
typed contract error when the cap is reached.
